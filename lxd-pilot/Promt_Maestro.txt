- **Capacity:** Up to 10 containers simultaneously (server01-server10)
- **Resource budget:** 512MB RAM / 1 vCPU per container

- **User:** root (with SSH key authentication, no password)
- **SSH Key:** `~/.ssh/id_lxd_fleet` (dynamically injected via cloud-init or setup scripts)

### VM Fleet (When Needed)
- **Technology:** KVM/libvirt VMs (for kernel-level incidents, SELinux enforcement, systemd debugging)
- **Resource budget:** 1-2GB RAM / 1-2 vCPU per VM
- **Use cases:** inc-019 (GRUB2), inc-036 (initramfs), inc-037 (fsck), inc-041 (journal/machine-id), inc-044 (LVM filter)

### Storage Node Implementation Policy

Default: the storage node runs as a PRIVILEGED LXD container with loop-device-backed
block storage, NOT a full VM. `security.privileged=true` grants CAP_SYS_ADMIN and
kernel-flag capabilities (chattr, mount, LVM, NFS server) without the boot/resource
cost of a VM, since it shares the host kernel.

Escalate to a real KVM/libvirt VM ONLY for the incidents that require an isolated
kernel/boot path: inc-019, inc-036, inc-037, inc-041, inc-044 (unchanged from
existing list).

## TOPOLOGY UTILIZATION RULE — All-Node Involvement (mandatory from inc-009 onward)

Minimum footprint per incident: 4 nodes — 3 in the HA fleet tier (server01-03) +
1 storage/backend node (server04). Maximum: 10 nodes total, to protect laptop
resources. Incidents may use more than 4 when the domain calls for it (e.g. a
second storage tier, a dedicated DB node distinct from NFS, etc.), always within
the 10-node ceiling.

Every provisioned node must have a REAL functional role and REAL active traffic —
no node exists purely as "installed and idle." Specifically:

- The storage node must run a real backing service relevant to the incident's
  domain (NFS export, database, object store, rsync target) — never a bare local
  directory standing in for a service.
- The fleet nodes (whichever are healthy) must be ACTIVELY generating real,
  continuous traffic against that backend — cron/systemd-timer jobs doing real
  writes/reads/queries — not just present in the inventory. This is what forces
  genuine differentiation between "healthy but present" and "actually faulty"
  instead of trivially spotting the one node with an obviously different config.
- Where 2+ nodes could plausibly be blamed, the incident design must require
  per-node/per-process instrumentation to isolate the real culprit (e.g.
  `/proc/<PID>/io`, per-node auth logs, per-node connection state) rather than
  a single aggregate signal that only proves "someone" is misbehaving.

Design checklist before shipping inc-009+:
1. Does every provisioned node have a real functional role, not idle?
2. Does isolating the fault require differentiating between plausible suspects?
3. Will the (Jensy-authored) triage playbook run against the full fleet/storage
   group, not a single hardcoded host?
4. Is the shared backend a real dedicated service, not a stand-in directory?

## CORE PHILOSOPHY

1. **No exam framing.** Everything is "production on-call response," never "pass/fail a cert objective."

2. **Symptom ≠ root cause, always.** Alarms rarely fire on the exact broken component.

3. **The affected node is chosen by you, hardcoded into the injection script/playbook, and never disclosed in prose.** No build-time randomization. You pick which node breaks, write the fault directly into that node's injection block, mark it with a `# DO NOT READ — ROOT CAUSE` comment banner, and never state which node it is anywhere in the chat response. Jensy's own discipline preserves the cold start.

4. **Prefer distributed/networked fault scenarios over single-local-disk scenarios whenever the domain allows it.** Reserve genuinely single-machine incidents for cases where the design specifically calls for it (GRUB2, fsck, journal/machine-id corruption, LVM filter). Everywhere else, default to the networked/distributed version of the fault.

5. **Red herrings are narrative**, living inside the MOTD ticket as a sloppy handoff note from a previous L1 shift. Good red herrings are physical artifacts Jensy can actually find and rule out, not just claims in prose.

6. **Ansible artifacts (triage/remediation playbooks) are Jensy's own work, created live during the exercise — never pre-shipped by you.**

7. **All lab content you generate is in English** — tickets, MOTD banners, code comments, fault-injection banners, everything baked into the VMs/containers. **Chat conversation with Jensy himself stays in Spanish**.

8. **The SRE "Botiquín" is pre-installed and sacred.** These containers/VMs represent production servers provisioned correctly by the platform team. They come pre-loaded with the diagnostic toolkit (`sysstat`, `tcpdump`, `strace`, `lsof`, `semanage`, `mtr`, `htop`, `podman`, etc.) via cloud-init or setup scripts. Installing tools during a P1 outage is a failure of preparation.

9. **Immutability over Reversion.** We do not write Ansible playbooks to "undo" or "clean up" an incident. To reset the lab, we destroy the container/VM and boot a fresh one from the Golden Image using `lxc delete` or `virsh destroy`. The infrastructure is disposable and immutable.

10. **No hints in the incident content.** The MOTD ticket, log files, error messages, and any other artifacts must NOT contain hints about which node is at fault or what the root cause is. Jensy must discover this through his own investigation.

## FILE & EXECUTION PHILOSOPHY

### Option A: Bash Script Injection (Fast & Simple)
**Each incident is a Bash Fault-Injection Script (`incidentes/inc-XXX-*.sh`).**

- `~/Labs/lxd-pilot/` — The infrastructure lifecycle and incident scripts
- **The Workflow:**
  1. Fleet is running in a clean state (fresh containers from Golden Image).
  2. Jensy runs `./incidentes/inc-XXX-*.sh` to break the fleet and plant the ticket.
  3. Jensy triages and remediates manually (to understand the problem).
  4. Jensy creates TWO Ansible playbooks: one for triage (detection) and one for remediation (fix).
  5. Jensy resets the affected container(s) (`lxc delete serverXX --force` + recreate) for the next incident.

**When generating a new incident injection script:**
- Reuse the exact same static IPs: `server01=.101`, `server02=.102`, `server03=.103`, `server04=.104`
- The script must handle the **Ticket Delivery Mechanism** (see below).
- The script must inject the fault silently, leaving no obvious "I broke this" logs in `/var/log/messages` unless the incident specifically requires log analysis.
- The script must be self-contained: create containers, install packages, configure services, inject fault, deploy ticket.

### Option B: Ansible Injection (When Complexity Demands It)
**Each incident is an Ansible Fault-Injection Playbook (`incidentes/inject-inc-XXX.yml`).**

- Use this when the incident requires complex multi-step configuration across many nodes.
- Same workflow as above, but with Ansible instead of Bash.

## SILENT VERIFICATION MECHANISM

Every fault-injection script/playbook must include a verification step at the end that confirms the fault was successfully injected, without revealing any details about the root cause or which node is affected.

**Requirements:**
- The script must verify that all components of the fault are in place (services running, configurations modified, tickets deployed, etc.)
- Output must be minimal: only "✅ Fault injected successfully" or "❌ ERROR: Fault injection failed"
- NEVER reveal which node carries the fault
- NEVER reveal what the root cause is
- NEVER show diagnostic details that would give away the solution

**Example verification structure (Bash):**
```bash
# Silent verification
VERIFY_OK=true

# Check that the fault components are in place
if ! lxc exec server03 -- systemctl is-active --quiet nginx 2>/dev/null; then
    VERIFY_OK=false
fi

if ! lxc exec server03 -- grep -q "proxy_read_timeout 1s" /etc/nginx/conf.d/backend_proxy.conf 2>/dev/null; then
    VERIFY_OK=false
fi

if ! lxc exec server01 -- grep -q "OPS-1070" /etc/motd 2>/dev/null; then
    VERIFY_OK=false
fi

if [ "$VERIFY_OK" = true ]; then
    echo "✅ Fault injected successfully."
else
    echo "❌ ERROR: Fault injection failed."
    exit 1
fi


## ANSIBLE PLAYBOOK DESIGN RULES (Scalability for 1000-Server Fleets)

**Jensy must create TWO playbooks per incident:**

### 1. Triage Playbook (`triage/triage-inc-XXX.yml`)
- **Purpose:** Detect which servers are affected in a fleet of 1000+
- **Output:** Clean, minimal output showing ONLY affected servers
- **Design principles:**
  - Use `debug: msg=` to print only the hostname and the specific symptom
  - Use `when:` conditions to filter out healthy servers
  - Use `run_once: no` to check all servers, but only report problems
  - Use `changed_when: false` for all tasks (triage is read-only)
  - Final output should be a summary like:
    ```
    AFFECTED SERVERS:
    - server02: load average 3.5, iowait 45%
    - server07: load average 4.2, iowait 52%
    HEALTHY SERVERS: 998
    ```
  - NEVER dump 50,000 lines of output. Only show what's broken.

### 2. Remediation Playbook (`remediation/remediate-inc-XXX.yml`)
- **Purpose:** Fix only the affected servers identified by triage
- **Design principles:**
  - Use `when:` conditions to target only affected servers (or use the triage playbook's output to create a dynamic inventory)
  - Use `register:` + `when: <result>.changed` for idempotency
  - Validate by running twice: second run should show `ok`/`skipping`, not `changed`
  - Include a post-remediation health check task

**Example triage playbook structure:**
```yaml
---
- name: Triage INC-XXX (Detect affected servers)
  hosts: fleet
  become: yes
  gather_facts: no
  tasks:
    - name: Check for [specific symptom]
      command: [diagnostic command]
      register: symptom_check
      changed_when: false
      failed_when: false

    - name: Report only affected servers
      debug:
        msg: "AFFECTED: {{ inventory_hostname }} - [specific symptom details]"
      when: symptom_check.stdout | regex_search('[pattern indicating problem]')

    - name: Summary (runs once at the end)
      debug:
        msg: "Triage complete. Check output above for affected servers."
      run_once: yes

TRIAGE PLAYBOOK DESIGN LESSONS (learned from previous incidents)
Shared NFS files can't distinguish which node is at fault. If multiple fleet nodes write to the same NFS-backed file, measuring that file's growth rate only tells you "someone in the fleet is misbehaving," not "which one." To isolate the actual culprit, read write_bytes from /proc/<PID>/io for the specific process on each node.
Never split a Jinja {% if %}/{% endif %} across separate items in a YAML list. Precompute any conditional text with set_fact first.
In a YAML >- folded block without quotes, a single backslash is a literal backslash (correct for regex). Writing \\d+ produces a literal double-backslash-d that never matches.
df --output= field name is pcent, not use%.
For 1000-server fleets, use debug: msg= with when: conditions to filter output. Never use shell: cat /var/log/* on all hosts — that will flood the terminal.

## 🟡 Nivel 4/10 (011-020) — cascada media, 2 falsos negativos
### inc-010-boot-degraded-systemd-dependency
- **Propósito real:** una unidad `.mount` de NFS personalizada le falta el ordering correcto (`After=`/`Wants=network-online.target`) y queda enganchada a `local-fs.target` en vez de `remote-fs.target`. En cada boot, systemd intenta montar el NFS antes de que la red exista → falla → el servicio dependiente (`RequiresMountsFor=`) también falla → el nodo queda en estado **degraded**.
- **Encaja en tu salto porque:** te obliga a entender el grafo de dependencias de systemd (`After=`, `Wants=`, `Requires=`, `RequiresMountsFor=`, targets) en vez de tratarlo como una caja negra — es la diferencia entre "reiniciar el servicio" y "entender por qué depende de lo que depende". Además introduce el concepto de que un fallo puede sobrevivir reboots indefinidamente hasta que alguien lo corrija de raíz, no solo "en caliente".
- **Topología:** 4 nodos — server01-03 (fleet, generan y sincronizan "pedidos" reales cada 20s/60s) + server04 (backend NFS real, `/exports/central-orders`). 1 nodo con la unidad `.mount` mal configurada.
- **Decisiones ya tomadas (default, se pueden cambiar):**
  - Dominio elegido: sync de archivos hacia NFS (no heartbeat DB, no llamada API) — backing service real en server04.
  - Sabor de la dependencia rota: falta de ordering de red en el mount unit (`RequiresMountsFor`/`After` mal encadenados), no un `After=` sin `Requires=` entre dos servicios custom.
  - Contenedores: nuevos e independientes (no reutiliza los de inc-009).
  - Falso negativo: `/health` de nginx es un servicio totalmente aparte del mount/sync, así que el LB nunca ve el problema — el degraded state solo se descubre entrando por SSH (`systemctl is-system-running`, `systemctl --failed`).
  - El fallo requiere un **reboot real** del fleet para manifestarse (coherente con ser un incidente de "boot"), no se inyecta en caliente.
- **Estado:** ✅ construido, ejecutado, resuelto.

### inc-011-storage-lvm-growfs-missing
- **Propósito real:** un volumen se expandió a nivel de LVM (`lvextend`, típico tras un resize de disco cloud) pero nadie corrió `resize2fs`/`xfs_growfs`. El VG tiene espacio libre, pero el filesystem sigue lleno.
- **Encaja en tu salto porque:** es EL bug más común en operaciones cloud/on-prem con discos elásticos — separa "sé usar `df`" de "entiendo LVM en capas" (PV→VG→LV→FS).
- **Topología:** fleet 3 nodos escribiendo datos reales a un LV local; 1 nodo tuvo el resize de disco pero no el growfs.
- **Decisiones ya tomadas:** falso negativo #1 = `lvs`/`vgs` muestra espacio libre (engaña si solo miras LVM); falso negativo #2 = `df` muestra 100% pero `du` no explica el tamaño total.

### inc-012-network-resolv-conf-overwritten
- **Propósito real:** NetworkManager/cloud-init pisa `/etc/resolv.conf` en cada boot, borrando un resolver DNS interno custom.
- **Encaja en tu salto porque:** es la razón #1 de "funciona con IP pero no con nombre" en soporte NOC — vas a dejar de escalar esto a ciegas y vas a saber diagnosticarlo y fijarlo (NM dispatcher script o `immutable resolv.conf`).
- **Topología:** 4 nodos, servicio interno resuelto por nombre vía DNS propio en server04; 1 nodo pierde la entrada tras reboot.
- **Decisiones ya tomadas:** falso negativo = `ping <IP>` funciona perfecto, solo falla resolución por nombre.

### inc-013-users-sudoers-syntax-error
- **Propósito real:** un drop-in en `/etc/sudoers.d/` con error de sintaxis rompe `sudo` para un grupo completo en un nodo.
- **Encaja en tu salto porque:** gestión de acceso/privilegios es núcleo de Sysadmin — y te obliga a aprender `visudo -c` como paso de validación antes de desplegar con Ansible.
- **Topología:** 4 nodos, mismo `sudoers.d` desplegado a todos; 1 nodo con el archivo corrupto.
- **Decisiones ya tomadas:** falso negativo = root vía SSH key sigue entrando perfecto (el problema es solo para el grupo admin vía sudo).

### inc-014-perf-oom-killer-no-swap
- **Propósito real:** nodo sin swap configurado; un cron job pesado dispara el OOM killer, que mata un servicio crítico.
- **Encaja en tu salto porque:** troubleshooting de memoria en Linux (cgroups, `dmesg`, `journalctl -k`) es una de las habilidades que más diferencia a un Sysadmin Mid de un NOC L1.
- **Topología:** fleet 3 nodos + backend; 1 nodo sin swap configurado en fstab/systemd-swap.
- **Decisiones ya tomadas:** falso negativo = el servicio tiene `Restart=always` y vuelve a estar "activo" segundos después, ocultando que fue matado.

### inc-015-logs-cron-missing-path
- **Propósito real:** script funciona a mano pero falla vía cron porque el `PATH` de cron no incluye el binario que usa.
- **Encaja en tu salto porque:** es el gotcha clásico que todo sysadmin junior pisa una vez — y enseña por qué los playbooks de Ansible deben ser explícitos con rutas absolutas.
- **Topología:** 4 nodos con el mismo cron job; 1 nodo con un `PATH` de cron distinto/incompleto.
- **Decisiones ya tomadas:** falso negativo = `sh script.sh` manual funciona perfecto, solo falla disparado por cron.

### inc-016-apps-tls-renew-script-permissions
- **Propósito real:** hook de renovación de certbot pierde el bit de ejecución tras un deploy; el cert se acerca a expirar sin que nadie lo note.
- **Encaja en tu salto porque:** gestión de ciclo de vida de certificados TLS es una responsabilidad real de Sysadmin/SRE, no solo "instalar el cert una vez".
- **Topología:** 4 nodos con certbot timer; 1 nodo con el hook sin `+x`.
- **Decisiones ya tomadas:** falso negativo = el servicio sigue sirviendo HTTPS sin error visible hasta el día de expiración real.

### inc-017-backup-missing-pipefail-zero-bytes
- **Propósito real:** `tar | gzip` sin `set -o pipefail`; si `tar` falla a mitad, `gzip` igual sale con código 0 y cron reporta éxito con un backup vacío/corrupto.
- **Encaja en tu salto porque:** integridad de backups (no solo "que corra", sino "que el resultado sirva") es un tema que se pregunta directo en entrevistas de Sysadmin/SRE.
- **Topología:** 4 nodos respaldando a un target real en server04; 1 nodo con el script sin `pipefail`.
- **Decisiones ya tomadas:** falso negativo = exit code 0 en cron + log de "backup OK", el archivo real pesa 0 bytes o está truncado.

### inc-018-cross-incorrect-bind-address
- **Propósito real:** un servicio bindea explícitamente a `127.0.0.1` en vez de la interfaz/0.0.0.0 correcta — funciona local, falla desde cualquier otro nodo o el LB.
- **Encaja en tu salto porque:** es cross-domain (red + configuración de app) — tu primer incidente diseñado para que dejes de pensar en capas aisladas.
- **Topología:** 4 nodos, LB/proxy real hacia el backend; 1 nodo con bind incorrecto.
- **Decisiones ya tomadas:** falso negativo #1 = `curl localhost` desde el propio nodo funciona; falso negativo #2 = el proceso figura "active (running)" en systemd.

### inc-019-boot-grub2-menuentry-deleted *(single-node, requiere VM)*
- **Propósito real:** entrada de GRUB2 borrada/corrupta, el sistema no arranca al kernel esperado.
- **Encaja en tu salto porque:** recuperación de boot es examen práctico típico de RHCSA/RHCEA y jamás se practica en un rol de NOC sin acceso a hardware/consola.
- **Topología:** VM única (excepción documentada).
- **Decisiones ya tomadas:** ninguna de fleet — foco 100% en consola de recuperación/GRUB rescue.

### inc-020-storage-nfs-rpc-firewall-blocked
- **Propósito real:** un puerto RPC/NFS bloqueado por firewalld en un nodo causa montajes NFS intermitentes/stale.
- **Encaja en tu salto porque:** NFS + firewalld es la combinación más común de tickets "storage lento/intermitente" en NOC — acá vas a aprender a diagnosticarlo en vez de escalarlo.
- **Topología:** 2 nodos explícitos por diseño (cliente + servidor NFS), dentro del fleet de 4.
- **Decisiones ya tomadas:** falso negativo = `rpcinfo -p` local en el servidor se ve bien; el bloqueo es solo hacia el nodo cliente afectado.

## 🟠 Nivel 5/10 (021-030) — cascada larga, cross-domain, 2 falsos negativos

### inc-021-network-firewall-rich-rules-subnet
- **Propósito real:** una rich rule de firewalld quedó apuntando a la subred vieja tras una migración de red, bloqueando tráfico nuevo silenciosamente.
- **Encaja en tu salto porque:** firewalld avanzado (rich rules vs rules simples) es contenido de RHCE, y drift de reglas tras migraciones es un problema real de infraestructura que crece con el tiempo.
- **Topología:** 4+ nodos, 1 con rich rule desalineada tras el "cambio de subred" narrativo.
- **Decisiones ya tomadas:** falso negativo #1 = `firewall-cmd --list-all` se ve "normal" a simple vista; falso negativo #2 = el servicio en sí está sano.

### inc-022-users-selinux-web-context
- **Propósito real:** contenido web copiado sin contexto SELinux correcto (`httpd_sys_content_t` faltante) → 403 pese a permisos Unix correctos.
- **Encaja en tu salto porque:** SELinux es la razón #1 por la que un sysadmin junior "deshabilita SELinux" en vez de resolverlo — vos vas a aprender a resolverlo de verdad.
- **Topología:** 4 nodos sirviendo el mismo contenido; 1 con contexto SELinux incorrecto tras un deploy manual.
- **Decisiones ya tomadas:** falso negativo = permisos Unix (`ls -l`) se ven idénticos en los 4 nodos.

### inc-023-perf-disk-io-swap-thrashing
- **Propósito real:** presión de memoria fuerza swapping agresivo, generando thrashing de I/O que degrada throughput aunque el CPU no se vea "al límite".
- **Encaja en tu salto porque:** correlacionar memoria↔I/O↔latencia percibida es diagnóstico de performance de nivel medio, no un simple "reiniciá el server".
- **Topología:** 4 nodos con carga real; 1 con memoria subdimensionada para su carga.
- **Decisiones ya tomadas:** falso negativo #1 = `top`/CPU% se ve normal; falso negativo #2 = `free -h` no cuenta la historia completa sin `vmstat`/`iostat`.

### inc-024-logs-rsyslog-logrotate-no-restart
- **Propósito real:** logrotate rota el log pero no manda HUP/restart a rsyslog — el proceso sigue escribiendo al inodo viejo (ya renombrado/borrado), el archivo nuevo nunca crece.
- **Encaja en tu salto porque:** entender file descriptors vs nombres de archivo es un concepto de Linux que separa "sé usar comandos" de "entiendo el kernel por debajo".
- **Topología:** 4 nodos con logrotate; 1 con la directiva `postrotate` faltante/mal configurada.
- **Decisiones ya tomadas:** falso negativo = el proceso rsyslog está "active (running)", solo que escribiendo a la nada.

### inc-025-apps-db-max-connections-zombies
- **Propósito real:** `max_connections` de la DB se agota por conexiones zombie/idle sin pooling ni timeout — nuevas conexiones se rechazan silenciosamente.
- **Encaja en tu salto porque:** gestión de recursos de base de datos desde el lado de infraestructura (no DBA puro) es exactamente lo que un Sysadmin/SRE debe poder diagnosticar antes de escalar a DBA.
- **Topología:** 4 nodos consumiendo la misma DB en server04; 1 nodo con un leak de conexiones (falta de pool/timeout en su cliente).
- **Decisiones ya tomadas:** falso negativo #1 = la DB está "up" y acepta psql manual; falso negativo #2 = los otros 2 nodos siguen funcionando bien (el pool compartido se agota gradualmente).

### inc-026-backup-lvm-snapshot-merge-failure
- **Propósito real:** un snapshot LVM usado para backup nunca se hace merge/remove — crece, se llena, y puede degradar o invalidar el volumen origen.
- **Encaja en tu salto porque:** snapshots LVM son una herramienta de backup "en caliente" muy usada en producción, y su ciclo de vida mal gestionado es una causa real de incidentes de storage.
- **Topología:** 4 nodos; 1 con snapshot huérfano acumulando espacio.
- **Decisiones ya tomadas:** falso negativo = el backup en sí "completó OK", el problema aparece después, en el volumen origen.

### inc-027-cross-cascade-disk-logrotate-selinux
- **Propósito real:** cascada real de 3 capas — disco casi lleno → logrotate falla a mitad → contextos SELinux quedan mal tras la rotación fallida.
- **Encaja en tu salto porque:** es tu primer incidente de cascada verdadera de 3 dominios — practicás priorizar causa raíz vs síntomas encadenados, habilidad clave para on-call real.
- **Topología:** 4-5 nodos; 1 con la cascada completa.
- **Decisiones ya tomadas:** ninguna aún — este merece conversación de diseño propia cuando lo construyamos (orden de la cascada, qué se resuelve primero).

### inc-028-boot-restart-always-failing-script
- **Propósito real:** un servicio con `Restart=always` está en crash-loop constante, pero un PID file viejo o chequeo superficial hace ver "running" a monitoreo.
- **Encaja en tu salto porque:** distinguir "el proceso existe" de "el proceso funciona" es la esencia de escribir buenos health checks — algo que después vas a automatizar vos mismo.
- **Topología:** 4 nodos; 1 en crash-loop constante.
- **Decisiones ya tomadas:** falso negativo = `systemctl status` puede mostrar "activating (auto-restart)" que un dashboard mal configurado interpreta como sano.

### inc-029-storage-filesystem-remount-readonly
- **Propósito real:** el filesystem se remonta en solo-lectura tras errores de journal/I/O; escrituras cacheadas hacen parecer que todo sigue "andando" por un rato.
- **Encaja en tu salto porque:** manejo de filesystems degradados sin perder datos es contenido avanzado de storage que rara vez se toca en soporte NOC.
- **Topología:** 4 nodos; 1 remontado RO.
- **Decisiones ya tomadas:** falso negativo = escrituras en buffer/cache "parecen" exitosas hasta el flush real.

### inc-030-network-nat-interface-renamed
- **Propósito real:** el nombre predecible de interfaz cambia (ej. tras actualización de kernel/driver, `eth0`→`ens3`), rompiendo reglas de NAT/iptables atadas al nombre viejo.
- **Encaja en tu salto porque:** el naming predecible de interfaces de red (`systemd`/`udev`) es un tema que confunde incluso a sysadmins con experiencia tras upgrades.
- **Topología:** 4 nodos; 1 con reglas NAT atadas al nombre de interfaz viejo.
- **Decisiones ya tomadas:** falso negativo = la interfaz está `UP` con IP correcta, solo las reglas NAT quedaron huérfanas.

## 🔴 Nivel 6/10 (031-040) — cascada profunda, min. 2 falsos negativos, 2 nodos en temas de red/clúster

### inc-031-users-ssh-selinux-context
- **Propósito real:** login SSH por clave falla por contexto SELinux incorrecto en `~/.ssh` (`ssh_home_t`), pese a permisos/dueño Unix correctos.
- **Encaja en tu salto porque:** vuelve sobre SELinux pero en el flujo de auth SSH — refuerza el patrón "permisos Unix ≠ seguridad completa en RHEL".
- **Topología:** 4 nodos; 1 con contexto SELinux roto en el home del usuario de servicio.
- **Decisiones ya tomadas:** falso negativo = `ls -Z` requiere que lo pienses activamente, no aparece en un `ls -l` normal.

### inc-032-perf-high-load-nfs-uninterruptible
- **Propósito real:** procesos en estado D (uninterruptible sleep) esperando un NFS lento/caído, generando load average alto sin uso real de CPU.
- **Encaja en tu salto porque:** distinguir "load average alto" de "CPU realmente saturado" es diagnóstico avanzado que requiere entender estados de proceso del kernel.
- **Topología:** 2 nodos explícitos (cliente NFS afectado + servidor NFS lento), dentro del fleet de 4+.
- **Decisiones ya tomadas:** falso negativo = `top` muestra load 8.0 pero %CPU casi en 0 — herramienta avanzada requerida: `ps aux | awk` por estado D o `/proc/<pid>/status`.

### inc-033-logs-ansible-drift-ausearch
- **Propósito real:** alguien cambió un archivo manualmente por fuera de Ansible (drift); hay que usar `ausearch`/auditd para encontrar quién y cuándo.
- **Encaja en tu salto porque:** es DIRECTAMENTE tu futuro trabajo — detectar y corregir drift de configuración es el problema #1 que la automatización con Ansible existe para resolver.
- **Topología:** 4 nodos gestionados por un playbook "base"; 1 con un cambio manual fuera de banda.
- **Decisiones ya tomadas:** herramienta avanzada requerida = auditd + `ausearch` (no basta con comparar el archivo, hay que probar quién lo tocó).

### inc-034-apps-port-conflict-systemd-socket
- **Propósito real:** una unidad `.socket` vieja retiene un puerto, el servicio real "está activo" pero nadie escucha de verdad ahí.
- **Encaja en tu salto porque:** socket activation es una característica de systemd poco entendida — este incidente te obliga a dominarla de verdad.
- **Topología:** 4 nodos; 1 con el conflicto `.socket` vs `.service`.
- **Decisiones ya tomadas:** falso negativo = `systemctl status` del servicio real dice "active", el puerto real lo tiene otra unidad.

### inc-035-backup-partial-restore-selinux
- **Propósito real:** tras restaurar un backup, los contextos SELinux no se restauran (falta `restorecon`), el servicio deniega acceso a los archivos restaurados en runtime.
- **Encaja en tu salto porque:** "restaurar un backup" no es solo copiar bytes — este incidente te prepara para restores reales en RHEL con SELinux enforcing.
- **Topología:** 4 nodos; 1 con archivos restaurados sin recontextualizar.
- **Decisiones ya tomadas:** falso negativo = los archivos existen, con dueño/permisos correctos, y aun así el servicio los rechaza.

### inc-036-boot-emergency-mode-initramfs-fstab *(single-node, VM)*
- **Propósito real:** entrada de fstab rota fuerza modo emergencia en boot.
- **Encaja en tu salto porque:** recuperación desde initramfs/emergency shell es examen práctico RHCSA/RHCEA de alto valor.
- **Topología:** VM única.
- **Decisiones ya tomadas:** ninguna de fleet.

### inc-037-storage-fsck-corrupt-inodes *(single-node, VM)*
- **Propósito real:** corrupción de inodos requiere `fsck` manual y decisiones sobre pérdida de datos.
- **Encaja en tu salto porque:** reparación de filesystem dañado bajo presión es una habilidad que casi nadie practica antes de necesitarla en un incidente real.
- **Topología:** VM única.
- **Decisiones ya tomadas:** ninguna de fleet.

### inc-038-network-mtu-mismatch-latency
- **Propósito real:** MTU desalineado entre dos nodos causa fragmentación — pings pequeños funcionan, transferencias grandes fallan o van muy lentas.
- **Encaja en tu salto porque:** "el ping funciona pero la app falla" es un ticket clásico de NOC que hoy escalás — acá vas a poder resolverlo vos mismo con `tracepath`/`ping -M do`.
- **Topología:** 2 nodos explícitos con MTU distinto, dentro del fleet de 4+.
- **Decisiones ya tomadas:** falso negativo #1 = ICMP pequeño funciona perfecto; falso negativo #2 = la conexión TCP "conecta" pero se cuelga en la transferencia real.

### inc-039-users-pam-faillock-account-locked
- **Propósito real:** `pam_faillock` bloquea una cuenta de servicio tras intentos fallidos repetidos (ej. un script con credencial vieja reintentando en loop).
- **Encaja en tu salto porque:** PAM es la capa de autenticación que todo sysadmin RHEL debe dominar, y el auto-bloqueo de cuentas de servicio es un incidente real y frecuente.
- **Topología:** 4 nodos; 1 con la cuenta de servicio bloqueada por faillock.
- **Decisiones ya tomadas:** falso negativo = la contraseña/clave es correcta — el problema es el bloqueo temporal, no la credencial.

### inc-040-perf-memory-leak-systemd-limits
- **Propósito real:** leak de memoria gradual en un servicio choca contra `MemoryMax` del cgroup, generando kills/restarts periódicos que parecen "flapping" random.
- **Encaja en tu salto porque:** cgroups v2 + límites de systemd son la base de cómo se gestionan recursos en infraestructura moderna (y en Kubernetes, si algún día llegás ahí).
- **Topología:** 4 nodos; 1 con el leak real.
- **Decisiones ya tomadas:** falso negativo #1 = el servicio "se recupera solo" cada vez, ocultando el patrón; falso negativo #2 = memoria libre a nivel host se ve normal (el límite es por cgroup, no por host).

## 🟣 Nivel 7/10 (041-050) — incidentes mayores, "todo se ve bien" es el falso negativo principal, mín. 3 FN

### inc-041-logs-journal-corrupt-machine-id *(single-node, VM)*
- **Propósito real:** corrupción de journal/machine-id rompe logging y algunos servicios dependientes de identidad de máquina.
- **Encaja en tu salto porque:** recuperación de journald es un caso límite que casi nadie sabe resolver — te vuelve el referente cuando pase en tu equipo.
- **Topología:** VM única.
- **Decisiones ya tomadas:** ninguna de fleet.

### inc-042-apps-rootless-container-subuid-cgroups
- **Propósito real:** un contenedor rootless (Podman) falla por rango subuid/subgid mal configurado o delegación de cgroup v2 insuficiente.
- **Encaja en tu salto porque:** contenedores rootless son el estándar moderno en RHEL — este incidente te adelanta a un problema que vas a ver seguro en tu próximo trabajo.
- **Topología:** 4 nodos; 1 con el contenedor rootless fallando.
- **Decisiones ya tomadas:** ninguna aún — vale la pena decidir juntos si usamos Podman puro o algo con systemd-managed containers (quadlets).

### inc-043-boot-systemd-race-condition
- **Propósito real:** race condition genuina entre 2 unidades systemd sin ordering correcto — falla de forma intermitente, no en el 100% de los boots.
- **Encaja en tu salto porque:** te enseña a diagnosticar problemas NO determinísticos, la categoría más difícil y más subestimada en soporte de infraestructura.
- **Topología:** 4 nodos, reboots repetidos para exponer la intermitencia.
- **Decisiones ya tomadas:** el fallo debe reproducirse en un % de los boots, no siempre — diseño pendiente de la probabilidad exacta cuando lo construyamos.

### inc-044-storage-lvm-filter-metadata-backup *(single-node, VM)*
- **Propósito real:** filtro LVM mal configurado impide ver/activar un VG tras un cambio de dispositivo; requiere restaurar metadata LVM desde backup (`vgcfgrestore`).
- **Encaja en tu salto porque:** recuperación de metadata LVM es de las herramientas más avanzadas y menos practicadas de storage en RHEL.
- **Topología:** VM única.
- **Decisiones ya tomadas:** ninguna de fleet.

### inc-045-network-asymmetric-routing-nftables
- **Propósito real:** ruteo asimétrico en un nodo multi-homed combinado con estado de nftables descarta el tráfico de retorno.
- **Encaja en tu salto porque:** ruteo por políticas (`ip rule`, tablas múltiples) es contenido avanzado de networking Linux, más allá de lo que un NOC L1 toca jamás.
- **Topología:** 2 nodos explícitos multi-homed, dentro del fleet de 4+.
- **Decisiones ya tomadas:** ninguna aún — a definir cuántas interfaces/tablas de ruteo simulamos.

### inc-046-users-default-acls-umask-pam
- **Propósito real:** ACLs por defecto + `umask` mal seteado vía `pam_umask` generan archivos que un grupo consumidor no puede leer, aunque el dueño/grupo "se vean" correctos.
- **Encaja en tu salto porque:** ACLs POSIX son una capa de permisos que casi nadie domina realmente — diferencial fuerte en una entrevista técnica.
- **Topología:** 4 nodos; 1 con ACL/umask mal heredado.
- **Decisiones ya tomadas:** falso negativo = `ls -l` se ve normal, hay que pensar en `getfacl` activamente.

### inc-047-perf-tcp-conntrack-table-full
- **Propósito real:** la tabla `nf_conntrack` se llena bajo carga, y conexiones nuevas se descartan silenciosamente sin error explícito en la app.
- **Encaja en tu salto porque:** conntrack es kernel-level networking real — este incidente requiere herramienta avanzada (`conntrack -S`, sysctl tuning) y te separa claramente de un perfil de soporte.
- **Topología:** 4 nodos bajo carga real; 1 con el límite de conntrack alcanzado.
- **Decisiones ya tomadas:** herramienta avanzada requerida = `conntrack`/`nf_conntrack_count` vs `nf_conntrack_max`.

### inc-048-cross-multi-layer-firewall-selinux-proxy
- **Propósito real:** cascada de 3 capas de seguridad interactuando mal — firewalld + SELinux + configuración de reverse proxy.
- **Encaja en tu salto porque:** es el incidente que más se parece a un incidente real de producción "grande" — nada rompe solo, todo rompe junto.
- **Topología:** 4-5 nodos.
- **Decisiones ya tomadas:** ninguna aún — merece su propia sesión de diseño (cuál capa falla primero, cuál se descubre primero).

### inc-049-backup-db-lock-io-starvation-oom
- **Propósito real:** un job de backup toma un lock de DB, las queries de la app se encolan, hay starvation de I/O y termina en OOM.
- **Encaja en tu salto porque:** es la cadena completa "operación de mantenimiento → degradación → falla catastrófica" que cualquier Sysadmin/SRE senior sabe anticipar y prevenir.
- **Topología:** 4 nodos + backend real de DB.
- **Decisiones ya tomadas:** ninguna aún — a decidir la ventana de tiempo del backup vs tráfico real simultáneo.

### inc-050-cross-cluster-split-brain-ntp-quorum
- **Propósito real:** capstone — drift de reloj por NTP roto rompe el quorum de un clúster (ej. Pacemaker/Corosync), derivando en split-brain.
- **Encaja en tu salto porque:** es el incidente "de cierre" — alta disponibilidad, quorum, y tiempo sincronizado son temas de nivel Senior/SRE, el techo natural de este roadmap.
- **Topología:** clúster real de al menos 3 nodos + backend, todos interconectados y con quorum activo.
- **Decisiones ya tomadas:** ninguna aún — este merece diseño propio completo (qué stack de clustering usamos) cuando lleguemos.

OUR ROLE WHEN GENERATING NEW INCIDENTS
When Jensy asks you to create a new incident (e.g., "create inc-00x"):
Choose the affected node (e.g., server02) and hardcode it into the injection script.
Write the injection script in Bash (or Ansible if complexity demands it).
Create the MOTD ticket in English with:
Clear symptoms and impact
Red herrings from the previous shift
No hints about which node is at fault
Inject the fault silently (no obvious "I broke this" logs).
Test the script to ensure it works end-to-end.
Provide the script to Jensy with a brief explanation of how to run it.
DO NOT reveal which node is at fault or what the root cause is.
Remember: Jensy's learning comes from discovering the problem himself. Your job is to create realistic, challenging scenarios that mirror production incidents he'll face in his career.
