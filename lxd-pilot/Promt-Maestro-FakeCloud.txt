## INFRASTRUCTURE — HYBRID (LXC + fakecloud)

### On‑Premise Tier (LXC Containers)
- **Technology:** LXD/LXC containers (lightweight, fast boot, low resource usage)
- **Nodes:** 3 containers (`server01`, `server02`, `server03`) — the application fleet
- **Resource budget:** 512MB RAM / 1 vCPU per container
- **Network:** Static IPs in `10.45.223.0/24` subnet (`101`, `102`, `103`)
- **OS:** AlmaLinux 9 (RHEL-compatible)
- **User:** root (SSH key authentication, no password)
- **SSH Key:** `~/.ssh/id_lxd_fleet` (injected via cloud-init or Terraform)
- **Role:** Run the application stack; one of them will carry the fault in each incident.

### Cloud Tier (fakecloud — Local AWS Emulator)
- **Technology:** **fakecloud** (LocalStack‑compatible emulator) running in its own LXC container or as a service on the host.
- **Services emulated:**
  - **S3** — object storage (buckets, objects, lifecycle policies)
  - **RDS** — relational database (PostgreSQL or MySQL)
  - **Route53** — private DNS resolution (e.g., `db.app.internal` → RDS endpoint)
  - **IAM** — identity and access management (users, roles, policies)
  - **CloudWatch** (optional) — basic metrics and alarms
- **Resource budget:** 1‑2GB RAM, 1‑2 vCPU (can be a container or a service on the host)
- **Access:** AWS CLI configured with `--endpoint-url` pointing to fakecloud.

### Monitoring Tier
- **Technology:** Prometheus + Alertmanager (or a lightweight alternative like `monit` + `node_exporter`)
- **Deployment:** As an LXC container or a systemd service on the host.
- **Role:** Scrape metrics from:
  - LXC nodes (CPU, memory, disk, network, custom app metrics)
  - fakecloud services (S3 bucket sizes, RDS connections, IAM usage)
- **Alerting:** Generates real alerts (simulated PagerDuty tickets) that appear in the MOTD or via a local webhook.

### Networking & DNS
- **Subnet:** `10.45.223.0/24` (LXD bridge)
- **Gateway:** `10.45.223.1`
- **DNS Resolution:**
  - LXC nodes use Route53 (fakecloud) for internal service discovery.
  - Example: `db.app.internal` resolves to the RDS endpoint (10.45.223.x).
- **Static IPs:** `server01=.101`, `server02=.102`, `server03=.103`
- **fakecloud services:** Get IPs in the same subnet (e.g., `.104` for S3, `.105` for RDS, `.106` for monitoring).

### Storage
- **Application logs:** Written to S3 buckets via AWS CLI (simulated).
- **Backups:** Stored in S3 buckets.
- **Shared state:** RDS database holds application state (simulated).

## TERRAFORM — The Single Source of Truth

All infrastructure is defined as **Terraform code** and deployed/destroyed with a single command.

**Key features:**
- **Provider:** `terraform-lxd/lxd` + `local` (for fakecloud setup).
- **Modules:** Separate modules for LXC nodes, fakecloud services, monitoring, and networking.
- **State:** Local file (or remote backend if desired).
- **Provisioners:** cloud‑init + remote‑exec to set up SSH keys, packages, and initial configurations.
- **Inventory:** Terraform generates a dynamic Ansible inventory (`inventory.ini`) after deployment.

**Workflow:**
1. `terraform apply -auto-approve` → < 2 minutes → full hybrid environment.
2. Run incident injection script (`./incidentes/inc-XXX.sh`).
3. Triage & remediate (manually, then with Ansible).
4. `terraform destroy -auto-approve` → clean slate for next incident.

### Incident Classification (by domain)
- **Linux‑only:** Fault resides entirely in the LXC node (systemd, filesystem, SELinux, networking, etc.).
- **Cloud‑only:** Fault resides in a fakecloud service (S3 bucket policy, RDS max connections, IAM role missing, DNS misconfiguration).
- **Hybrid:** Fault spans both domains (e.g., an app cannot write to S3 because its IAM role expired, causing local logs to fill up disk on the LXC node).

### Red Herrings & Previous Shift Notes
- Always included in the MOTD ticket.
- Must be plausible and physical (e.g., "We saw error X and restarted service Y, but it didn't help").
- Must never hint at the actual root cause or the affected node.

### 🟡 Level 4/10 (011-020)

#### inc-011-storage-lvm-growfs-missing (Linux-only)
- **Problem:** LVM volume extended but filesystem not grown.
- **Topology:** 3 LXC nodes + fakecloud S3 for backup logs. One node affected.
- **Environment:** LXC privileged + loop device (NO VM needed).
- **Mechanism:** sparse file → `losetup` → `pvcreate`/`vgcreate datavg` → `lvcreate datalv` (~400MB) → `mkfs.ext4` → mount `/data` → fill to 90%. Fault: `lvextend` to 100%FREE but NO `resize2fs`. Deterministic.
- **Verify:** `df /data` ≥ 90% AND `vgs` Free > 0 AND `resize2fs -P` < LV size.
- **False negatives:** `lvs` shows free space; `df` shows 100%; `du` doesn't explain total.
- **LXD gotcha:** needs `modprobe loop` on host + privileged (already in fleet profile).

#### inc-012-network-resolv-conf-overwritten (Linux-only)

- **Topology:** 3 LXC nodes + Route53 (fakecloud). One node loses its resolver.
- **Environment:** LXC.
- **Mechanism:** Write custom `resolv.conf` + a NM dispatcher that wipes it on `up`. Deterministic on reboot.
- **Verify:** After reboot, `/etc/resolv.conf` lacks the custom nameserver; `getent hosts <internal>` fails.
- **False negatives:** Ping by IP works; only name resolution fails.

#### inc-014-perf-oom-killer-no-swap (Linux-only) — REFRAME

#### inc-043-boot-systemd-race-condition (Linux-only) — REFRAME
- **Problem:** Two systemd units misordered → dependent fails on boot.
- **Topology:** 3 LXC nodes.
- **Environment:** LXC. **REFRAME:** true races are non-deterministic in LXD (fast, consistent boot). Convert to a deterministic ordering bug.
- **Mechanism:** Service B `Requires=` A, but A reads a file that doesn't exist at boot (like inc-010's `EnvironmentFile`). Fails every boot. Deterministic.
- **Verify:** `systemctl is-system-running` = degraded on exactly one node; reproducible every reboot.
- **False negatives:** Works if you manually restart A then B after boot.
- **LXD gotcha:** Avoid timing races; use missing-file / broken-dependency faults.

#### inc-046-users-default-acls-umask-pam (Linux-only)

## ⚠️ HARD CONSTRAINTS & LESSONS LEARNED (MANDATORY FOR ALL INCIDENTS)

These rules encode REAL failures hit while building this lab. Every incident
(inc-011 → inc-050) MUST comply. Ignoring them reproduces broken infrastructure.

### 1. Base Image — ALWAYS the cloud variant
- USE: `almalinux9-cloud` (alias of `images:almalinux/9/cloud`). It ships cloud-init.
- NEVER use base `images:almalinux/9` → no cloud-init → user-data, SSH keys and
  packages silently fail. Symptom: Ansible/SSH `Connection refused` on port 22.

### 2. Terraform resource — ALWAYS `lxd_instance`
- Use `resource "lxd_instance"` with `type = "container"`.
- `lxd_container` is DEPRECATED (warnings, will be removed).

### 3. Networking — ALWAYS DHCP, NEVER static via network-config
- Let LXD assign IPs via DHCP on `lxdbr0`; reference nodes by name or by the DHCP
  IP captured in the generated `inventory.ini`.
- NEVER use `user.network-config` for static IPs → cloud-init fails with
  "Address default is not a valid ip address/network" and the node boots broken.

### 4. FakeCloud — host service, NOT a container
- FakeCloud runs as a systemd service ON THE HOST (mx) at `http://10.45.223.1:4566`.
- DO NOT create a `fakecloud` LXD container. Reach it from fleet nodes via
  `aws --endpoint-url http://10.45.223.1:4566`.
- `10.45.223.1` is the `lxdbr0` gateway, reachable from every container.

### 5. AWS CLI — install AND configure on every node that talks to FakeCloud
- Install `awscli` in base packages.
- Inject `/root/.aws/credentials` (test/test) and `/root/.aws/config` (region=us-east-1).
- AWS CLI refuses to run without credentials + region even though FakeCloud ignores
  them ("Unable to locate credentials" / "You must specify a region").

### 6. ⚠️ FAULT INJECTION — LXD networking is INSTANT (the #1 gotcha)
- LXD containers bring networking up immediately at boot. There is NO network race.
- These fault types DO NOT REPRODUCE — do NOT use them:
  - Missing `After=network-online.target` / `Wants=network-online.target`.
  - NFS / S3 / network mount races at boot.
  - `Before=network-online.target` tricks or `ExecStartPre` network checks.
- USE DETERMINISTIC FAULTS (trigger reliably regardless of boot timing):
  - Missing required file: `EnvironmentFile=/path` (no `-` prefix), missing `ExecStart`
    binary, `ConditionPathExists=` pointing to a nonexistent path.
  - Broken config syntax: sudoers, fstab, systemd unit, SELinux context.
  - Removed package/binary, changed permissions/ownership, firewall rules.
  - LVM / filesystem state changes.

### 7. Boot-degraded incidents — the reliable recipe
To guarantee `systemctl is-system-running` returns `degraded`:
1. Backend service (e.g. `s3-backend.service`) reads a required `EnvironmentFile=/etc/xxx.env`.
2. Dependent service declares `Requires=<backend>` + `After=<backend>`.
3. Fault = DELETE the `.env` file on the target node.
4. On reboot systemd can't load the missing EnvironmentFile → backend fails →
   dependent fails → boot = `degraded`.
5. Keep `/health` (nginx) as an INDEPENDENT unit so it still returns 200 (blind spot).

### 8. Three-layer architecture (mandatory)
- Layer 1 — Terraform (`main.tf`): infra COMMON to ALL incidents: containers, SSH keys,
  base packages (python3, openssh, awscli, nginx, rsync, curl, bind-utils),
  Node Exporter + textfile collector, Prometheus, inventory.ini. Deployed ONCE.
- Layer 2 — Ansible (`incidentes/inc-XXX/setup.yml`): incident-specific app. Idempotent.
  Deploys scripts, systemd units, S3 buckets, Prometheus alert rules.
- Layer 3 — BASH (`incidentes/inc-XXX/inject-fault.sh`): ONLY injects fault + MOTD +
  reboot + silent verify. Keep under ~120 lines. Not idempotent by design.

### 9. Ansible templating gotcha
- Embedding Prometheus rules (Go-template `{{ }}`) in Ansible `copy.content` breaks Jinja2
  (`unexpected char '$'` on `{{ $labels.instance }}`).
- Fix: escape as `{{ '{{' }} $labels.instance {{ '}}' }}` or wrap in `{% raw %} ... {% endraw %}`.

### 10. Inventory hygiene
- Never name an Ansible group `localhost` (collides with the implicit localhost host). Use `[local]`.

### 11. Monitoring — make it real, not decorative
- Each incident's `setup.yml` MUST inject a Prometheus alert rule relevant to the fault.
- Use the Node Exporter textfile collector (`/var/lib/node_exporter/textfile_collector/*.prom`)
  to expose custom app metrics (e.g. `order_sync_success 0/1`).
