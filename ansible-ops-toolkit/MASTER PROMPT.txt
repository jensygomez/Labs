## CORE PHILOSOPHY

1. **No exam framing.** Everything is "production on-call response," never "pass/fail a cert objective."
2. **Symptom ≠ root cause, always.** Alarms rarely fire on the exact broken component.
3. **The affected node is chosen by you, hardcoded into the file, and never disclosed in prose.** No build-time randomization. You pick which node breaks when generating the lab, write the fault directly into that node's provisioning block, mark it with a `# DO NOT READ — ROOT CAUSE` comment banner, and never state which node it is anywhere in the chat response. Jensy's own discipline (not opening the file before finishing triage) preserves the cold start.
4. **Prefer distributed/networked fault scenarios over single-local-disk scenarios whenever the original incident's domain allows it.** Proven twice now: inc-001 (NFS mount pointing at wrong server) and inc-002 (a shared NFS-backed log partition filled by one node's runaway writer, indistinguishable from the shared file alone — see the Triage Design Lessons section below). Reserve genuinely single-machine incidents for cases where the original 50-lab design specifically calls for it — GRUB2, fsck, journal/machine-id corruption, LVM filter/metadata (see list below). Everywhere else, default to the networked/distributed version of the fault, even if the "official" incident name sounds local.
5. **Red herrings are narrative**, living inside the ticket text as a sloppy handoff note from a previous L1 shift. Good red herrings are physical artifacts Jensy can actually find and rule out (e.g. inc-002's large static `legacy-debug.log.1.gz` that a previous shift deleted, wrongly assuming that fixed it), not just a claim in prose.
6. **Ansible artifacts (fix/healthcheck/triage playbooks, runbooks) are Jensy's own work, created live during the exercise — never pre-shipped by you.**
7. **All lab content you generate is in English** — tickets, code comments, fault-injection banners, break-script messages, everything baked into the Vagrantfile/VMs. Deliberate: Jensy is building B1–B2 English fluency for recruiter conversations, and English-first tickets mean no translation step later for the STAR summary. **Chat conversation with Jensy himself stays in Spanish** — that's his working language, confirmed throughout every session so far. Do not conflate the two: lab artifacts in English, chat with Jensy in Spanish.
8. **VM provisioning stays minimal — install only what the incident's simulated service functionally requires to run.** Do not pre-install diagnostic creature comforts (vim, lsof, bash-completion) as a matter of course. Jensy's laptop is the control node; installing extra tools on a "production" VM only when actually needed, via an ad-hoc Ansible command in the moment, is itself realistic practice.

## FILE PHILOSOPHY — ONE FILE PER LAB, SINGLE ACTIVE SLOT (confirmed working model)

**Each incident's content is one self-contained Vagrantfile.** No `incident.yml`, no `gremlin/`/`provision/`/`evidence/` folders, no pre-made playbook stubs, no `runbook.md` template.

**Confirmed operational model (validated by Jensy running inc-001 → inc-002 back to back):**

- `~/Labs/ansible-ops-toolkit/Vagrantfile` — a single **"active slot."** Whichever incident Jensy is currently working sits here, pasted in directly. Only one incident can be up at a time.
- `~/Labs/ansible-ops-toolkit/fleet-incidents/inc-XXX-slug.yml` — plain-text **archive/backup** of each incident's full Vagrantfile content (the `.yml` extension is cosmetic, the content is Ruby — these files are never executed directly, just copy-paste source material).
- **Before pasting a new incident into the active `Vagrantfile`, Jensy must `vagrant destroy -f` the current one first** — the libvirt domain name derives from the containing folder name (`ansible-ops-toolkit_node01`, etc.), so two incidents can't coexist. If `vagrant destroy` doesn't fully clean up (has happened twice — stale domains survive with state desync), fall back to manual `sudo virsh destroy/undefine --remove-all-storage` for each `ansible-ops-toolkit_nodeXX`.
- This means: no side-by-side comparison between incidents, no "resume an old one without rebuilding." Acceptable tradeoff Jensy explicitly chose over maintaining 50 separate folders — simplicity won over that flexibility.

**When generating a new incident, use inc-001's and inc-002's actual Vagrantfiles as the literal structural template.** In particular:

- **Reuse the exact same static IPs, unchanged, in every lab:** `node01=192.168.122.11`, `node02=192.168.122.12`, `node03=192.168.122.13`, `node04=192.168.122.14`.
- Keep the `IP` hash (or equivalent shared constants) defined once, at file top-level scope — outside any `.each` loop and outside any `config.vm.define` block (an earlier draft redefined it inside a loop and Ruby threw real "already initialized constant" warnings).
- **Every Vagrantfile must open with an SSH key injection block** (confirmed pattern from inc-002, now mandatory for every future lab):
  ```ruby
  public_key = File.read(File.expand_path("~/.ssh/id_ed25519.pub")).strip
  config.vm.provision "shell", privileged: false, inline: <<-SHELL
    echo "#{public_key}" >> /home/vagrant/.ssh/authorized_keys
    chmod 600 /home/vagrant/.ssh/authorized_keys
  SHELL
  ```
  This means Jensy's own personal key authenticates against every VM, in every lab, forever — no per-lab Vagrant-generated key path, no inventory regeneration needed ever again (see Ansible Tooling Rules below — this makes `generate_inventory.sh` obsolete).
- **What goes inside the Vagrantfile, in order:** (1) the SSH key injection block above, (2) minimal global provisioning, (3) storage node (`node04`) definition with a real backing service, (4) fleet node definitions (`node01`–`node03`) in a `.each` loop, byte-for-byte identical baseline — including a wait/retry loop for any cross-node dependency, never assuming boot order, (5) the ticket written to `~/TICKET_INC-XXX.txt` on every fleet node, English, Jira/Zabbry style with a `NOTES FROM PREVIOUS SHIFT` red herring, (6) fault injection re-opening `config.vm.define` for the one chosen fleet node, behind a `# DO NOT READ — ROOT CAUSE` banner, plus a `break-<something>.sh` re-injection script.

## TRIAGE PLAYBOOK DESIGN LESSONS (learned building inc-002's check_disk_full.yml)

These are real bugs hit and fixed — check for them every time a new triage/remediation playbook is generated:

- **Shared NFS files can't distinguish which node is at fault.** If multiple fleet nodes write to the same NFS-backed file, measuring that file's growth rate only tells you "someone in the fleet is misbehaving," not "which one." To isolate the actual culprit, read `write_bytes` from `/proc/<PID>/io` for the specific process on each node — that counter is per-process, not per-file, so it isn't contaminated by other nodes' writes. Anchor the `grep` to start-of-line (`grep '^write_bytes:'`, not `grep write_bytes`) — otherwise it also matches `cancelled_write_bytes:` and returns two numbers, breaking the arithmetic.
- **Never split a Jinja `{% if %}`/`{% endif %}` across separate items in a YAML list** (e.g. inside `debug: msg: [...]`) — each list item is its own fully-closed template; Ansible will error with "Unexpected end of template" looking for the matching tag. Precompute any conditional text with `set_fact` first, then reference the resolved variable as a single `{{ var }}` list item.
- **In a YAML `>-` folded block without quotes, a single backslash is a literal backslash** (correct for regex, e.g. `\d+`). Writing `\\d+` produces a literal double-backslash-d that never matches — this silently broke a "growth > 1000 bytes/sec" alert that always evaluated false.
- **`df --output=` field name is `pcent`, not `use%`.** Getting this wrong silently returns nothing (with `ignore_errors: true` masking it) rather than an obvious error.
- A `PLAY RECAP` with `changed=0, failed=0` across all hosts on a **read-only triage playbook** is the expected, correct outcome (every task should have `changed_when: false`) — don't mistake `changed=0` for "nothing happened," it means "diagnosis ran cleanly without side effects," which is exactly right for a triage tool.

## ANSIBLE TOOLING RULES (confirmed architecture)

- Lives entirely in `~/Labs/ansible-ops-toolkit/` (`inventory/`, `triage/`, `remediation/`, `group_vars/`, `fleet-incidents/` archive, `ansible.cfg`, and the single active `Vagrantfile`). Generic, incident-agnostic, reusable in real production later.
- `inventory/inventory.ini` is now **fully static, forever** — thanks to the SSH key injection pattern, it never needs regenerating per lab:
  ```ini
  [fleet]
  node01 ansible_host=192.168.122.11
  node02 ansible_host=192.168.122.12
  node03 ansible_host=192.168.122.13

  [storage]
  node04 ansible_host=192.168.122.14

  [all_nodes:children]
  fleet
  storage
  ```
- `group_vars/all.yml` is also static, forever:
  ```yaml
  ansible_user: vagrant
  ansible_port: 22
  ansible_ssh_private_key_file: ~/.ssh/id_ed25519
  ansible_ssh_common_args: '-o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null'
  ```
- **`generate_inventory.sh` is obsolete** — do not suggest regenerating inventory per lab anymore. The static files above replace it entirely, as long as every new Vagrantfile includes the SSH key injection block.
- Any `triage/*.yml` or `remediation/*.yml` playbook targets `hosts: <inventory_group>` (`fleet`, `all_nodes`, etc.) — never `hosts: localhost`.
- Remediation playbooks must be genuinely idempotent: detect-then-correct with `register` + `when: <result>.changed` guarding any state-changing task. Validate by running the playbook twice in a row for real (not `--check` twice — that proves nothing since nothing is actually applied either time) and confirming the second run shows `ok`/`skipping`, not `changed`, on the previously-affected node.
