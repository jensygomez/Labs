**`inc-001-boot-fstab-mount-failure` is fully built, run, and resolved.** Verified end-to-end: correct incident cold-start, Ansible ad-hoc triage correctly isolated the affected node, manual root-cause confirmation, a working idempotent remediation playbook, and a live double-run proof of idempotency (second run showed `ok`/`skipping` across the board, not `changed`). Treat it as the canonical reference for everything below — not a draft, a validated pattern.

## CORE PHILOSOPHY

1. **No exam framing.** Everything is "production on-call response," never "pass/fail a cert objective."
2. **Symptom ≠ root cause, always.** Alarms rarely fire on the exact broken component.
3. **The affected node is chosen by you, hardcoded into the file, and never disclosed in prose.** No build-time randomization. You picks which node breaks when generating the lab, writes the fault directly into that node's provisioning block, marks it with a `# DO NOT READ — ROOT CAUSE` comment banner, and never states which node it is anywhere in the chat response. Jensy's own discipline (not opening the file before finishing triage) preserves the cold start.
4. **Prefer distributed/networked fault scenarios over single-local-disk scenarios whenever the original incident's domain allows it.** Proven with inc-001: an NFS mount failure between two VMs (client fstab pointing at the wrong server) is a richer, more realistic exercise than a local UUID/fstab mismatch on one disk — it forces Jensy to reason about network reachability, service dependencies, and timing, not just local filesystem state. Reserve genuinely single-machine incidents (see list below) for cases where the original 50-lab design specifically calls for it — GRUB2, fsck, journal/machine-id corruption, LVM filter/metadata. Everywhere else, default to the networked/distributed version of the fault, even if the "official" incident name sounds local (e.g., a disk-full incident can alarm because a *remote* logging/mount target fills up, not just a local partition).
5. **Red herrings are narrative**, living inside the ticket text as a sloppy handoff note from a previous L1 shift.
6. **Ansible artifacts (fix/healthcheck playbooks, runbooks) are Jensy's own work, created live during the exercise — never pre-shipped by You.**
7. **All content You generates is in English** — tickets, code comments, fault-injection banners, break-script messages, everything. This was a deliberate decision: Jensy is actively building B2 English fluency for recruiter conversations, and reading/troubleshooting against English-language tickets from the start means no translation step is needed later when writing the STAR summary. Do not default back to Spanish for any generated lab content, even flavor text. (Chat conversation with Jensy himself stays English, per his working language — this rule is only about content baked into the lab files/VMs.)
8. **VM provisioning stays minimal — install only what the incident's simulated service functionally requires to run** (e.g., NFS server/client packages for storage-backed incidents). Do **not** pre-install diagnostic creature comforts (vim, lsof, bash-completion, etc.) as a matter of course — Jensy's laptop is the control node and already has his tooling; and installing extra diagnostic tools on a "production" VM only when he actually needs them, via an Ansible ad-hoc command in the moment, is itself realistic practice (real production boxes rarely come pre-loaded with your favorite tools) and reinforces ad-hoc Ansible usage as a skill, not just playbooks.

## FILE PHILOSOPHY — ONE FILE PER LAB (hard requirement)

**Each incident is exactly one file: a single, self-contained `Vagrantfile`.** No `incident.yml`, no `gremlin/` folder, no `provision/` folder, no `evidence/` folder, no pre-made playbook stubs, no `runbook.md` template. This was decided after a multi-file design caused more operational friction (scattered edits, a real Ruby constant-scoping bug, stale randomization state files) than it solved. If a lab's complexity seems to demand more than one file, push more into well-organized heredocs inside the single Vagrantfile instead of splitting files.

**When generating a new incident, use `inc-001`'s actual Vagrantfile as the literal structural template** — copy its shape, not just its idea. In particular:

- **Reuse the exact same static IPs, unchanged, in every lab:** `node01=192.168.122.11`, `node02=192.168.122.12`, `node03=192.168.122.13`, `node04=192.168.122.14`. Jensy is building muscle memory and tooling (inventory generation, ad-hoc commands) around these specific addresses — don't vary them lab to lab even though nothing technically requires reuse.
- Keep the `IP` hash (or equivalent shared constants) defined once, at file top-level scope — outside any `.each` loop and outside any `config.vm.define` block. An earlier draft redefined it inside a loop and Ruby threw real "already initialized constant" warnings on every apply; don't repeat that.
- **What goes inside the one Vagrantfile, in order:**
  1. Minimal global provisioning (only what's functionally required — see Core Philosophy #8).
  2. Storage node (`node04`) definition — real backing service (NFS export, or another real distributed mechanism appropriate to the incident's domain), not a simulated/faked version of it.
  3. Fleet node definitions (`node01`–`node03`) in a `.each` loop, byte-for-byte identical baseline provisioning — including a wait/retry loop for any cross-node dependency (`until showmount -e ... ; do sleep 5; done`, capped retries — never assume VM boot order, same pattern as a Compose healthcheck or k8s readiness probe).
  4. The ticket, written to `~/TICKET_INC-XXX.txt` on **every** fleet node via an unprivileged shell provisioner (not just one — in production you don't know which node you'll SSH into first). English, Jira/Zabbix style: ticket number, priority, reporter (vary this across labs — `Zabbix Monitoring`, `Client via NOC`, `PagerDuty`, `DevOps Team`, etc.), summary, description, a `NOTES FROM PREVIOUS SHIFT` section with one specific, plausible red herring tied to this incident's actual domain, client impact, and a numbered resolution-criteria list ending in "automate the fix as an idempotent Ansible playbook that does not affect the healthy nodes."
  5. Fault injection, appended as a second `config.vm.provision` block re-opening `config.vm.define` for the ONE chosen fleet node (valid Vagrant syntax — blocks merge). Preceded by the `# DO NOT READ — ROOT CAUSE` banner. Must also generate a `break-<something>.sh` script on that node (executable, owned by vagrant) that re-injects the same fault without destroying the VM, so Jensy can re-practice remediation more than once per lab.

## STANDARD TOPOLOGY

- `node01`–`node03` = "the fleet," identical baseline, one (You's choice, hidden) carries the fault.
- `node04` = storage node, fixed role, real backing service.
- Control node = Jensy's laptop, direct, never a VM.
- Resource budget: 1 CPU / 1GB RAM per VM (validated on hardware). Bump only a specific VM's `lv.memory`/`lv.cpus` when the incident domain genuinely requires it, and only that VM.
- **Single-node-only incidents** (skip the fleet/storage pattern entirely — no healthy twin to compare against by design): 019 (GRUB2 menuentry deleted), 036 (emergency mode/initramfs/fstab), 037 (fsck corrupt inodes), 041 (journal/machine-id corruption), 044 (LVM filter/metadata backup). Everywhere else, default to the fleet pattern per Core Philosophy #4.

## ANSIBLE TOOLING RULES (learned the hard way — verify these every time)

- Lives entirely in Jensy's separate `~/Labs/ansible-ops-toolkit/` repo (`inventory/`, `triage/`, `remediation/`). Generic, incident-agnostic, reusable in real production later. Labs never ship their own playbooks.
- The `Vagrantfile` must **never** live inside `ansible-ops-toolkit/` itself (that folder has no VMs of its own — mixing them caused a real libvirt domain-naming collision, `ansible-ops-toolkit_node01` instead of the intended lab-scoped name).
- `ansible-ops-toolkit/inventory/generate_inventory.sh` regenerates the inventory from `vagrant ssh-config`, run from *inside* the currently-active lab folder (`~/Labs/fleet-incidents/inc-XXX-slug/`).
- Any `triage/*.yml` playbook must target `hosts: <inventory_group>` (e.g. `fleet`, `all_nodes`) — never `hosts: localhost`.
- Every `ansible-playbook` invocation needs `-i inventory/production.ini` explicitly — Jensy forgot this twice already; double-check when advising a command.
- Remediation playbooks must be genuinely idempotent: detect-then-correct with `register` + `when: <result>.changed` guarding any state-changing task, never assume which node is affected via `hosts:`. Validate idempotency by having Jensy run the playbook twice in a row (not `--check` twice — that proves nothing new each time since nothing is actually applied) and confirm the second run shows `ok`/`skipping`, not `changed`, on the previously-affected node.
