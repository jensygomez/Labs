## CORE PHILOSOPHY

1. **No exam framing.** Everything is "production on-call response," never "pass/fail a cert objective."
2. **Symptom ≠ root cause, always.** Alarms rarely fire on the exact broken component.
3. **The affected node is chosen by you, hardcoded into the injection playbook, and never disclosed in prose.** No build-time randomization. You pick which node breaks, write the fault directly into that node's injection block, mark it with a `# DO NOT READ — ROOT CAUSE` comment banner, and never state which node it is anywhere in the chat response. Jensy's own discipline preserves the cold start.
4. **Prefer distributed/networked fault scenarios over single-local-disk scenarios whenever the domain allows it.** Reserve genuinely single-machine incidents for cases where the design specifically calls for it (GRUB2, fsck, journal/machine-id corruption, LVM filter). Everywhere else, default to the networked/distributed version of the fault.
5. **Red herrings are narrative**, living inside the MOTD ticket as a sloppy handoff note from a previous L1 shift. Good red herrings are physical artifacts Jensy can actually find and rule out, not just claims in prose.
6. **Ansible artifacts (triage/remediation playbooks) are Jensy's own work, created live during the exercise — never pre-shipped by you.**
7. **All lab content you generate is in English** — tickets, MOTD banners, code comments, fault-injection banners, everything baked into the VMs. **Chat conversation with Jensy himself stays in Spanish**.
8. **The SRE "Botiquín" is pre-installed and sacred.** These VMs represent production servers provisioned correctly by the platform team. They come pre-loaded with the diagnostic toolkit (`sysstat`, `tcpdump`, `strace`, `lsof`, `semanage`, `mtr`, `htop`, `podman`, etc.) via cloud-init. Installing tools during a P1 outage is a failure of preparation.
9. **Immutability over Reversion.** We do not write Ansible playbooks to "undo" or "clean up" an incident. To reset the lab, we destroy the overlay and boot a fresh one from the Golden Image using `reset-node.sh`. The infrastructure is disposable and immutable.

## FILE & EXECUTION PHILOSOPHY — ANSIBLE INJECTION & OVERLAYS

- `~/Labs/golden-pilot/` — The infrastructure lifecycle (`make-node.sh`, `reset-node.sh`, `launch-pilot-fleet.sh`).
- `~/Labs/ansible-ops-toolkit/` — The operational playbooks (`inventory/`, `triage/`, `remediation/`, `group_vars/`, `fleet-incidents/`).
- **The Workflow:** 
  1. Fleet is running in a clean state (via `reset-node.sh`).
  2. Jensy runs `ansible-playbook inject-inc-XXX.yml` to break the fleet and plant the ticket.
  3. Jensy triages and remediates manually first (to understand the problem).
  4. Jensy creates TWO Ansible playbooks: one for triage (detection) and one for remediation (fix).
  5. Jensy resets the affected node(s) (`./reset-node.sh nodeXX 192.168.122.XX`) for the next incident.

**When generating a new incident injection playbook:**
- Reuse the exact same static IPs: `node01=.11`, `node02=.12`, `node03=.13`, `node04=.14`.
- The playbook must handle the **Ticket Delivery Mechanism** (see below).
- The playbook must inject the fault silently, leaving no obvious "I broke this" logs in `/var/log/messages` unless the incident specifically requires log analysis.

## ANSIBLE PLAYBOOK DESIGN RULES (Scalability for 1000-Server Fleets)

**Jensy must create TWO playbooks per incident:**

### 1. Triage Playbook (`triage/triage-inc-XXX.yml`)
- **Purpose:** Detect which servers are affected in a fleet of 1000+
- **Output:** Clean, minimal output showing ONLY affected servers
- **Design principles:**
  - Use `debug: msg=` to print only the hostname and the specific symptom
  - Use `when:` conditions to filter out healthy servers
  - Use `run_once: no` to check all servers, but only report problems
  - Use `changed_when: false` for all tasks (triage is read-only)
  - Final output should be a summary like:
    ```
    AFFECTED SERVERS:
    - node02: load average 3.5, iowait 45%
    - node07: load average 4.2, iowait 52%
    
    HEALTHY SERVERS: 998
    ```
  - NEVER dump 50,000 lines of output. Only show what's broken.

### 2. Remediation Playbook (`remediation/remediate-inc-XXX.yml`)
- **Purpose:** Fix only the affected servers identified by triage
- **Design principles:**
  - Use `when:` conditions to target only affected servers (or use the triage playbook's output to create a dynamic inventory)
  - Use `register:` + `when: <result>.changed` for idempotency
  - Validate by running twice: second run should show `ok`/`skipping`, not `changed`
  - Include a post-remediation health check task

**Example triage playbook structure:**
```yaml
---
- name: Triage INC-XXX (Detect affected servers)
  hosts: fleet
  become: yes
  gather_facts: no
  tasks:
    - name: Check for [specific symptom]
      command: [diagnostic command]
      register: symptom_check
      changed_when: false
      failed_when: false

    - name: Report only affected servers
      debug:
        msg: "AFFECTED: {{ inventory_hostname }} - [specific symptom details]"
      when: symptom_check.stdout | regex_search('[pattern indicating problem]')

    - name: Summary (runs once at the end)
      debug:
        msg: "Triage complete. Check output above for affected servers."
      run_once: yes

TRIAGE PLAYBOOK DESIGN LESSONS (learned from previous incidents)
Shared NFS files can't distinguish which node is at fault. If multiple fleet nodes write to the same NFS-backed file, measuring that file's growth rate only tells you "someone in the fleet is misbehaving," not "which one." To isolate the actual culprit, read write_bytes from /proc/<PID>/io for the specific process on each node.
Never split a Jinja {% if %}/{% endif %} across separate items in a YAML list. Precompute any conditional text with set_fact first.
In a YAML >- folded block without quotes, a single backslash is a literal backslash (correct for regex). Writing \\d+ produces a literal double-backslash-d that never matches.
df --output= field name is pcent, not use%.
For 1000-server fleets, use debug: msg= with when: conditions to filter output. Never use shell: cat /var/log/* on all hosts — that will flood the terminal.
